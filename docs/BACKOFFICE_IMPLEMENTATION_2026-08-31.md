# 后台原型落地记录

日期：2026-08-31

## 基准与范围

以 `backoffice-prototype-v2.html` 及 `BACKOFFICE_PROTOTYPE_BUSINESS.md` 为界面与交互参考。正式实现沿用 React / Vinext、D1、R2 和已有业务接口，不引用原型的虚构商户、订单或 sessionStorage 数据。

入口仍是商家 `/merchant`、平台运营 `/admin`；商城与平台门户不改为后台外观。

## 已落地的正式界面

| 区域 | 页面与行为 |
| --- | --- |
| 共用框架 | 左侧可展开的分组菜单、当前功能高亮、角色内功能搜索、面包屑、移动端菜单、退出入口。商家与平台不互相显示角色切换按钮。 |
| 数据展示 | 商品、库存、营销、成员、订单、售后、申请、站点、域名、媒体、版本、操作记录使用表格，支持搜索、空结果和本地分页。 |
| 二级页面 | 新增、编辑、处理、详情与列表分离；通过当前记录 ID 查找，缺失记录明确提示，不退化成第一条记录。 |
| 商品 | 名称、路径、介绍、分类字符串、图片上传与媒体绑定、价格、SKU、多规格选项、销售状态。PATCH 使用真实 productId；已有商品库存从库存页维护。 |
| 商品导入 | CSV / JSON 文件先调用 dryRun；确认后写入目录。JSON 先与已加载目录合并，CSV 使用现有服务端合并规则。 |
| 库存 | 当前 SKU、总量、锁定量、可售量、增减数量；服务端继续执行不可低于锁定量的校验。 |
| 营销 | 优惠券、组合商品、集合、推荐规则、活动排期分别有专用字段；不把商品表单套用到营销创建。 |
| 店铺成员 | 邮箱与真实店铺岗位、负责人保护、移除确认。不虚构“邮件已发送”。 |
| 订单 | 指定订单详情、商品、地址、物流、备注、退款和状态记录；发货与备注独立提交。 |
| 商家退款 | 负责人和管理员可调用新的商家权限入口，继续复用原 PayPal 退款流程。状态以真实返回为准；本入口不自动补库存、不自动重试付款方请求。 |
| 售后 | 登记订单号、邮箱、类型、金额和原因；处理页记录状态与结论，不把结案当作退款成功。 |
| 商户申请 | 列表进入单条申请，分为审核、交付、域名申请、工单、通知、历史。切换审核选项不会自动提交。补资料和拒绝需原因。 |
| 商户站点 | 站点列表、三步代建、单站点交付详情；已有申请从申请详情创建并关联负责人。 |
| 域名 | 绑定表单、解析/证书详情、真实检查。重复提交本店域名保留真实 ID 和核验状态；其他店铺域名不可被抢占。 |
| 站点协作者 | 成员列表、邀请与角色表单、邀请记录、移除和撤销。此处是现有站点级 CMS 协作权限，不冒充完整的平台员工权限系统。 |
| 运营工具 | 现有支付、邮件、交付、发布、健康检查改为选择对应业务分区后显示，不同时展开所有工具。 |
| 平台订单协查 | 读取订单、商品、退款、备注、邮件与支付回调；保留异常重试。日常发货、退款和库存调整在商家后台。 |

## 保留真实能力边界

以下原型字段没有对应正式数据模型，本轮不添加伪保存，也不据此宣称生产功能全量完成：

- 多级分类实体与排序：现有分类是商品字段，仅提供分类汇总与关联商品入口。
- 客户分组和商家客户备注：现有消费者账户接口属于消费者本人；商家只从当前加载的订单汇总客户和关联订单，没有越权调用消费者账户接口。
- 商品重量、物流公司、独立库存调整原因：现有接口不支持；本轮不悄悄丢弃表单输入。
- 平台岗位和可服务商户范围：沿用现有站点协作角色，未新增平台级任意角色。
- 店铺成员邀请有效期：现有成员接口按邮箱授予权限，不等于完整邮件邀请生命周期。
- 原型的模拟回调、自动库存回补及“DNS 模拟成功”：未带入正式代码。
- 独立模板库：沿用现有站点模板复制能力，不假设存在独立行业模板管理模型。

这部分要完整实现，需要单独扩展数据模型、权限和 API，不能通过 UI 改版代替。

## 数据安全与交互

- 切换店铺时清空商家子页面数据，取消初始请求，并防止旧店铺响应覆盖新店铺。
- 平台等待当前站点数据加载后再显示业务内容，避免旧站点表格绑定新站点操作。
- 新业务表单有保存中、错误、禁用状态；常规页面导航和关闭窗口时提示未保存修改。
- 保留服务端授权；按钮隐藏不是授权替代。
- 生产密钥不写入原型或项目文档；构建没有修改线上数据库。
- 支付回调、退款完成、邮件投递、发货状态仍分别记录，不用一个“成功”覆盖整个流程。
